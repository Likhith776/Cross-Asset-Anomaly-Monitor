[ 01 ] Detection

Two paths write to the same anomaly table.

Every price tick is scored the instant it arrives, and every five minutes a second pass re-checks the last hundred readings per symbol for anything the first pass would only catch in hindsight.

Path AReal-time · per tick

Tick-level detectors

Runs the moment a quote lands, before it's written anywhere else.

  • 01 Z-score spike against the rolling window
  • 02 Isolation forest on multivariate feature vectors
  • 03 Cross-asset correlation break vs. tracked pairs
Path BBatch · every 5 minutes

Composite scoring

Re-scores the last 100 feature rows per symbol with a weighted blend, and writes a generated description with each hit.

  • 01 Z-score, recomputed over a longer horizon
  • 02 EWMA volatility surge
  • 03 PCA residual across the tracked universe

High-severity hits (score ≥ 0.7) can carry a one- to two-sentence explanation from a single Gemini call, strictly grounded in the feature snapshot — no news speculation. It's off by default, capped at 6 calls/hour and 30/day, and any failure just leaves the field null; the anomaly itself is always written first.

[ 02 ] Architecture

The same detectors, two different bodies.

Slim is one process for anyone who wants to just run it. Full streaming is the event-driven topology underneath it, for scaling out.

Yahoo / Finnhub── 30s fetch loop ──▶src/slim.py (one process)
├─ingest thread → features → 3-detector pipeline → alerts
├─batch thread → composite scoring / 5 min
├─daily threads → retention cleanup, backup
└─FastAPI :8000
▼
PostgreSQL — market_anomaliesStreamlit dashboard :8501

Working set ≈ 0.9 GB including OS. Runs on a laptop, a small box, or a 1 GB free-tier VM. No Docker, no broker.

Yahoo / Finnhub (producer)──▶Kafka — topic: market-data
├──▶feature-consumer — z-score, EWMA, PCA, correlation snapshots
└──▶anomaly-consumer — tick-level pipeline
▼
PostgreSQL — market_features · anomaly_events · correlation_snapshots
▼
scheduler — batch detection / 5 min, cleanup / dailyFastAPI :8000Streamlit :8501

8 containers, KRaft-mode Kafka (no Zookeeper). Same detector modules as slim — never a fork, just more infrastructure around them.

[ 03 ] Deployment

The public instance runs on nothing you have to keep on.

The hosted version is a scheduled GitHub Actions workflow that runs the detection pipeline on GitHub's own runners and publishes straight to GitHub Pages.

DEPLOY · GITHUB

Zero infrastructure

No server, no database to maintain, no card on file, no dependence on any personal machine staying awake.

github.io / live-data branch
STATE · WARM

Warm-started state

Detection state persists in the published tree between runs, so each run continues from the last one instead of ramping from cold.

state/ committed each cycle
INCIDENTS · LOG

Shareable incident log

Every real anomaly the deployed system has actually caught, with severity, regime, and lead-lag context, regenerated on a fixed schedule.

refreshed every 30 min

Prefer to self-host? The slim profile needs only Python, Postgres, and about a gigabyte of RAM — front it with a free Cloudflare Tunnel and it's public with no port forwarding. The Docker profile ships Prometheus and Grafana alongside it, with a provisioned "Cross-Asset Pipeline Health" dashboard covering fetch latency, consumer lag, per-detector execution time, and DB write failures.

[ 04 ] Run it yourself

Two profiles, four commands to a running dashboard.

# 1. configure — DATABASE_URL is the only required value cp .env.example .env # 2. first run only: create tables and seed demo data python scripts/init_db.py # 3. fetch + detect + API, one process python -m src.slim # 4. dashboard, second terminal streamlit run dashboard/app.py → localhost:8501 · localhost:8000/docs
# 1. configure (optional: add a Finnhub key for real-time crypto/FX) cp .env.example .env # 2. start everything docker compose up -d --build # 3. first run only: tables + 7 days of demo data DATABASE_URL=postgresql://postgres:password@localhost:5432/market_anomalies \ python scripts/init_db.py → same dashboard/API URLs as the slim profile
